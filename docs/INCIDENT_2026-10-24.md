# Incident 2026-10-24: RAM exhaustion, API restart loop, leaked processes

**Window:** 2026-10-24 00:00–04:45 Lisbon (WEST, UTC+1) = 2026-10-23 23:00 – 2026-10-24 03:45 UTC.
**Impact:** RAM 27.5 / 31.6 GB with 9.5 GB in the pagefile and CPU at about 85 %. Imports ran about 10× slower
(`import app.api.main` 61 s). API cold start took about 2.5 min, so the supervisor restarted the API 32 times
between 02:25 and 04:36 Lisbon. The hourly news DAG was blocked for about 3.5 h. No data loss: 2026-10-23 was
finalised by the second attempt at 04:49 UTC.

## Root causes

1. **Leaked processes (about 1 GB per hour).** The leaks were filler `prices_global_yf` job processes, not the
   news jobs. CTRL+BREAK hit the whole task tree: the taskrun crashed and the job process deadlocked in its own
   exit. `kill_tree()` follows parent pids, and `TaskProc.poll()` only watched the root, so a descendant whose
   parent had died was invisible. The news jobs close their pools properly (`Streamer` is a context manager).
2. **news_finalise "hang".** It was not a deadlock. py-spy showed the main thread in `as_completed` while the
   parse workers were busy unzipping and parsing. The causes were a large catch-up day (341 downloads),
   oversubscribed threads (no thread cap in the pool workers) and paging. A bounded reproduction on copied inputs
   (8 files, same machine) took 82 s and peaked at 1.3 GB with the default threads, against 38 s and 0.57 GB with
   2 threads per worker. The 180-min timeout plus 1 retry kept the hourly DAG blocked
   ("maximum instances reached").
3. **API restart loop and the orphaned API.** Health checks counted from 90 s after spawn whatever the port state
   was, used a fixed 10 s timeout, and restarted after 5 s with no back-off. The stray API pair was not owned by
   the supervisor. Nothing detected it, and `kill_tree` from the venv launcher cannot reach an interpreter whose
   launcher already exited.
4. **Filler concurrency.** RAM admission used the parent-pid tree (orphans uncounted) and CC-NEWS's 2 GB estimate.
   No rule kept the heavy campaigns (E6, CC-NEWS) from running next to other tasks.
5. **PAUSE vs running tasks.** The governor did request a stop. CC-NEWS, however, only checked its STOP file
   between WARCs and waited for every in-flight WARC (about 1 GB each). The filler then waited out the full
   900 s module grace.
6. **The machine guard never fired.** The free-RAM rule (< 3 GB) did not trigger at 4 GB free, while 9.5 GB was
   in the pagefile.

## Fixes

| Area | Change |
|---|---|
| `app/ops/winsys.py` | `JobObject` (KILL_ON_JOB_CLOSE, nested), `start_in_job()` (created suspended → assigned → resumed: no start-up race with the venv launcher), `process_cmdline/image/cwd/create_time`, `listening_pids(port)`, `pressure_sample()` (pagefile proxy). `pid_alive()` now uses the process object's signalled state, so a process stuck in exit counts as alive. |
| `app/ops/supervisor.py` | One Job Object per child. Readiness = port open (cold start up to 5 min). Health every 60 s with a 10 s timeout, or 30 s under pressure or after a failure. Exponential restart back-off (10 s → 10 min). A `stopping` state means a new instance never starts until the old job is empty. Before an API start the port is cleared (stray `app.cli serve api` of ours killed; a foreign holder → `external`). Housekeeping every 5 min runs the reaper and the stray-API check. Status gains per-child restart reasons, `restarts_30m`, an alert after 3 restarts in 30 min, and reaper metrics. |
| `app/ops/reaper.py` (new) | Kills `multiprocessing.spawn` children whose parent is dead, only when they run our interpreter with a cwd inside this installation. Also finds stray APIs: by default it kills those on our port or orphaned ones, and warns about others (`BIG360_SUPERVISOR_STRAY_API=all\|off`). |
| `app/scheduler/runner.py` | A Job Object per process job. Every descendant dies at end, failure or timeout, and leftovers are logged as "leak prevented". Job processes turn CTRL+BREAK into KeyboardInterrupt (normal exit, no DLL-teardown deadlock). Machine guard: process jobs wait up to 10 min under pressure; `news_finalise` is deferred instead. |
| `app/ops/tasks.py`, `filler.py`, `governor.py`, `taskrun.py` | A Job Object per filler task, with leftovers killed when the root exits. RAM is measured per job. Heavy tasks (E6, CC-NEWS, GDELT redo) run alone. Pause and pressure stops use `pause_grace_s` (180 s). Machine guard adds a pagefile-growth rule (+1 GB in 5 min while free RAM < 6 GB). taskrun handles CTRL+BREAK gracefully. |
| `app/events_v2/ccnews.py`, `hist_merge.py` | STOP is honoured within 60 s (in-flight WARCs abandoned and redone next run). Child joins are bounded (3 h). |
| `app/events_v2/pipeline.py` | At most `max_inflight` (4 × workers) files downloaded but not yet parsed. `parse_threads` caps Polars/OMP/MKL in pool workers. Optional `mem_budget_mb`. |
| `app/news_live/compaction.py`, `jobs.py`, `contracts/jobs.yaml` | Finalise: 2 workers × 2 threads, 8 files in flight, 3 GB hard budget for the tree. ## What to monitor

- `/system/status` → `supervisor.children.api.restarts_30m` (alert at ≥ 3) and `restart_reasons`.
- `supervisor.reaper.leaked_processes`, which should stay 0. A non-zero `killed_total` after the first sweep means
  something still leaks.
- Worker and filler logs: "leftover process(es) … killed (leak prevented)" names the job or task that leaked.
- `data/state/news_live.json` → `finalise_attempts`: a day with n ≥ 3 is backing off. Check the job log.
- Data Health → filler `sample.pagefile_growth_gb` / `free_ram_gb`, and governor reasons ("pagefile growing").
- `supervisor.json` → `children.*.rss_mb` (job-wide RSS, orphaned descendants included).

## Operator switches

- `data/state/ops/filler.PAUSE`: pause the filler (running tasks stop within about 3 min).
- `data/state/ops/news_finalise.HOLD`: defer the daily finalise. A manual run uses job param `force=true`.
- `BIG360_SUPERVISOR_REAPER=0`: disable reaper and stray-API housekeeping.
  `BIG360_SUPERVISOR_STRAY_API=all|off`: change the stray-API policy.
- `BIG360_API_COLD_START_S` (300), `BIG360_FINALISE_MEM_MB` (3072), `BIG360_PRESSURE_GUARD=0` (disables the
  worker's pressure deferral).

## Addendum: the three "unkillable" orphans (pids 37616, 61584, 49584)

These were the leaked processes. `taskkill` reported "no running instance" and .NET reported `HasExited=True`,
yet each still held about 0.9 GB private memory. Read-only inspection at about 06:10 UTC:

- **Stuck inside their own exit.** The exit status was set, but the process object was never signalled.
- **One thread left**, waiting with reason 37 = `WrAlertByThreadId`. That is the wait used by SRW locks, condition
  variables and `WaitOnAddress`; a pending kernel I/O wait would show Executive/WrRundown instead.
- **No handles left.** A census of the system handle table (SystemExtendedHandleInformation) found 0 handles for
  all three; a normal process holds about 128. So they were **not** stuck on a DuckDB file, a named pipe to the
  dead parent, a socket, a temp file or an SMB path (`data/` is local), because the kernel had already closed
  all of them.

Exit status 0xC000013A (STATUS_CONTROL_C_EXIT) means the exit was started by the console's default CTRL+BREAK
handler, which calls ExitProcess. By contrast, every process killed *externally* during the night exited
completely: the finalise attempt-1 tree at 03:38 and the CC-NEWS tree at 04:02. A terminating process cannot be
cut short by TerminateProcess. The three processes disappeared on their own between 06:12 and 06:18 UTC, after
4–6 h; free RAM rose from 5.0 to 8.4 GB. The cause of the final wait is not proven. A kernel debugger would be
needed, and listing filter drivers (`fltmc`) requires admin. A third-party exit callback is possible; the only
security product registered is Windows Defender.

Changes:

- **Detection.** `winsys.exiting(pid)` and `pid_running(pid)`. `pid_alive()` now reports such processes as alive,
  because they still hold memory.
- **Reaper.** These processes are classified as `zombie`: they are logged once, reported in
  `supervisor.reaper.zombies` / `zombie_mb` and in the `zombie_processes` alert, and never retried.
- **Supervisor.** A zombie never blocks a restart: `_gone()` ignores it and logs an error. The finalise run
  marker treats a zombie as stale.
- **Prevention 1.** Job processes now start in their **own process group** (`runner._start_in_own_group`), so a
  CTRL+BREAK sent to the worker's or a taskrun's group reaches neither them nor their pool workers.
- **Prevention 2.** Children with a STOP file (worker, filler, realtime) get **no CTRL+BREAK** from the
  supervisor. They stop through the file, and after the grace period their Job Object is killed externally,
  which always completes. Only the API (uvicorn, no pools) still gets CTRL+BREAK.
- **Prevention 3.** Job processes map SIGBREAK to KeyboardInterrupt, and pools are closed by their context
  managers.
